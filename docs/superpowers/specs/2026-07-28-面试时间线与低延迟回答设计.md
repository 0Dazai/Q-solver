# 面试时间线与低延迟回答设计

## 1. 目标

Q-Solver 的面试模式应在完全本地管理会话数据的前提下：

1. 同时展示面试官问题、AI 参考答案、求职者实际回答。
2. 保存可上滑浏览、重启后可重新打开的面试历史。
3. 自动生成求职者可直接阅读和编辑的 Markdown 面试记录。
4. 让已解析简历和本地资料库实际参与回答。
5. 采用低延迟流式口语答案，减少真实面试中的等待。

## 2. 消息模型

每场面试建立独立会话，每条消息包含：

- `id`：消息唯一标识。
- `session_id`：面试会话标识。
- `turn_id`：所属问答轮次。
- `question_id`：关联问题标识。
- `role`：`interviewer`、`ai_suggestion` 或 `candidate`。
- `content`：最终正文。
- `partial_content`：仅用于界面实时显示的临时转写。
- `status`：`streaming`、`final`、`cancelled` 或 `error`。
- `created_at`、`updated_at`：本地时间。

角色含义：

- `interviewer`：系统音频识别出的面试官问题。
- `ai_suggestion`：AI 以求职者第一人称生成的参考答案。
- `candidate`：本机麦克风识别出的求职者实际回答。

同一个问题只在时间线出现一次。候选问题的实时识别在该消息内部更新，提交后转为最终问题，不再在面板顶部重复显示。

## 3. 前端交互

面试主区域采用统一时间线：

```text
面试官
请介绍一下你的项目经历。

AI 参考
我在项目中主要负责……

我的回答
我当时负责的是……
```

交互规则：

1. 时间线支持鼠标滚轮和触控板上滑查看历史。
2. 用户位于底部时，新消息自动跟随。
3. 用户已上滑时保持当前位置，并显示“有新消息”按钮。
4. AI 答案按流式内容更新同一条消息。
5. 求职者讲话时显示实时转写，收到 final 后追加到当前轮次的“我的回答”。
6. 下一道问题到达后，上一轮所有内容仍保留。
7. 保留问题编辑、重新提交、深入分析、取消生成和资料来源入口。
8. 提供“打开 Markdown”“打开记录目录”“生成面试复盘”操作。

## 4. 本地持久化

### 4.1 SQLite

在当前 Windows 用户的 Q-Solver 数据目录中保存：

- 面试会话元数据。
- 三类时间线消息。
- 每轮问题、AI 答案、本人回答及状态。
- Markdown 文件路径。

数据库写入通过单独的存储服务串行执行，不阻塞 ASR 音频发送或模型流式回调。

### 4.2 Markdown

默认目录：

`文档\Q-Solver\面试记录`

每场会话对应一个 Markdown 文件，名称包含开始时间和会话短标识。内容包括：

- 会话开始和结束时间。
- 使用的简历、回答模型和资料策略。
- 每轮面试官问题。
- 每轮 AI 参考答案。
- 每轮求职者实际回答。
- 用户主动生成的面试复盘。

Markdown 在消息 final 或 AI 流式回答结束时异步刷新。写入采用临时文件加原子替换，避免程序退出时留下半份文件。

## 5. 简历和资料上下文

1. PDF 解析结果继续保存在 `ResumeContent`。
2. 保存解析结果时同步建立本地分块索引。
3. 面试模式打开或监听启动时，先构建候选人会话上下文：
   - 完整简历 Markdown。
   - 用户标记为“面试常驻”的 Markdown 资料。
   - 从上述内容提取的紧凑候选人档案。
4. 候选人档案保存在当前本机会话内，并在第一道问题出现前完成准备。
5. 对兼容无状态接口，每轮请求携带紧凑候选人档案；模型端支持会话状态或提示缓存时可复用，但不把该能力作为正确性前提。
6. 完整简历与常驻 Markdown 超出上下文预算时，保留紧凑档案，并按当前问题补充相关原文片段。
7. 本地资料库检索与简历相关片段检索并行执行。
8. 上下文设置明确字符预算，优先顺序为：
   - 当前问题。
   - 预载候选人档案。
   - 与问题相关的简历或常驻 Markdown 原文。
   - 本地资料库依据。
   - 最近一轮求职者实际回答。
9. 云端向量增强不进入首答关键路径。

前端显示“候选人资料准备中 / 已就绪 / 需重新准备”。简历或常驻资料发生变化时，使现有预载上下文失效并在下一次面试前重建。

## 6. 固定面试角色提示

面试模型始终获得内置系统提示，用户配置的面试提示作为补充附加。内置提示要求：

- 当前任务是求职面试回答辅助。
- AI 扮演求职者并使用第一人称。
- 输出自然、口语化、可直接表达的回答。
- 优先使用简历和本地资料中的真实经历。
- 不虚构公司、项目、职责、成果或数字。
- 信息不足时采用保守、可说明边界的表达。
- 先给结论，再给两到三个支撑点。
- 默认控制在约 150–350 个汉字。
- 不输出分析过程，也不提及 AI、提示词、检索或资料库。

## 7. 低延迟链路

采用方案三：低延迟流式口语答案。

### 7.1 问题确认

- 对稳定的 partial/final 片段提前执行本地预检索。
- 检测到疑问词、问号、明确句尾或停顿后，使用约 450–800ms 的自适应等待。
- 语句明显未结束时继续聚合，避免把半句话提交给模型。

### 7.2 并行准备

问题趋于稳定时并行执行：

- 从已预载候选人档案读取稳定上下文。
- 简历和常驻 Markdown 相关原文片段检索。
- 本地资料库检索。
- 最近本人回答整理。
- 模型请求参数准备。

最终问题确认后复用预检索结果；文本变化明显时再执行一次短检索。

### 7.3 模型请求

- 面试默认使用低推理强度。
- 默认回答预算约 150–350 个汉字。
- 流式第一批文字立即进入时间线。
- “深入分析”才使用更长输出和更高推理等级。
- 本地检索采用短超时；超时后以已获得的简历摘要和通用知识继续首答。

### 7.4 非阻塞任务

以下操作不进入首答串行链路：

- SQLite 记录写入。
- Markdown 文件刷新。
- 来源卡片整理。
- 云端向量增强。
- 面试复盘生成。

## 8. 目标指标

- 明确句尾后的问题确认：约 450–800ms。
- 面试开始前候选人上下文已完成预载，不计入单题回答延迟。
- 本地检索：目标 50–200ms。
- 软件侧在问题确认后立即发起模型请求。
- 模型首批文字到达后立即显示，不等待完整答案。
- 正常网络和快速模型下，界面目标为约 2 秒级出现首段答案。

模型服务端排队和网络延迟单独记录，避免与软件内部耗时混淆。

## 9. 错误处理

- 本地记录失败：在界面提示记录状态，继续语音和答案链路。
- Markdown 刷新失败：保留 SQLite 数据，下次打开会话时重新生成。
- 简历检索失败：继续使用资料库和通用回答。
- 资料检索超时：直接启动回答，不等待云端增强。
- 模型流中断：保留已收到内容，消息标记为 `error`，允许重新提交。
- ASR 重连：保留当前会话和已有时间线，不创建重复轮次。

## 10. 测试与验收

### 后端

- 三角色消息的创建、更新、轮次关联和重启恢复。
- 同一问题只创建一个面试官消息。
- AI 流式片段更新同一消息。
- 本人 final 转写写入对应轮次。
- 简历内容进入检索和回答上下文。
- 内置面试角色提示始终存在，用户提示作为补充。
- SQLite 和 Markdown 写入失败不阻塞回答。
- 自适应提交和短检索超时。

### 前端

- 三类消息视觉区分。
- 历史可上滑。
- 底部自动跟随和上滑后的“有新消息”行为。
- 问题不再重复。
- 本人历史回答在新问题出现后仍可见。
- 重启后加载本地历史。

### 实机

- 使用系统音频产生面试官问题。
- 使用麦克风产生求职者实际回答。
- 验证 AI 流式首屏。
- 暂停、恢复和重启后检查时间线与 Markdown。
- 检查 F9 共享画面隔离状态未受影响。
